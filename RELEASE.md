# Release versioning and recovery

## Chrome-compatible release versions

Chrome requires `manifest.json` `version` to be one to four dot-separated integers.
A GitHub prerelease may use a suffix such as `2026.10.1-Beta2`, but that
suffix belongs in the extension's display-only `version_name`, not `version`.

For the current Beta2 release:

- GitHub release tag: `2026.10.1-Beta2`
- `package/manifest.json`: `"version": "2026.10.1"` and
  `"version_name": "2026.10.1-Beta2"`
- `package.json` and the two root version entries in `package-lock.json`:
  `2026.10.1`
- Expected artifact: `send-to-home-assistant-v2026.10.1-Beta2.zip`

The release workflow runs `scripts/validate-release.js` and rejects mismatched
tags, base versions and prerelease display names. **Do not remove the version
check to get around a failed release.**

For future versions, update all version fields **before creating the release
tag**. Keep the numeric Chrome version strictly increasing for Chrome Web Store
updates; merely changing the prerelease display name does not create an
upgradable browser extension version.

## Recover the existing 2026.10.1-Beta2 release

The existing Beta2 tag points at the earlier merge commit. Re-running the
original failed release job checks out that older commit, including its outdated
manifest and release workflow. Fixes committed to `main` do not rewrite an
existing published tag.

Once this release-workflow fix is merged to `main`:

1. Open **GitHub Actions > Package and Release Extension > Run workflow**.
2. Select **main** and enter **2026.10.1-Beta2** for `release_tag`.
3. Run the workflow. It requires an existing release and verifies the original
   tag is an ancestor of the current main commit. It also checks the numeric
   version, prerelease display name, full test suite and ZIP packaging.
4. Verify the downloadable asset
   `send-to-home-assistant-v2026.10.1-Beta2.zip` appears on the existing
   [Beta2 release](https://github.com/JOHLC/Send-to-Home-Assistant/releases/tag/2026.10.1-Beta2).

This recovery deliberately keeps the original tag unchanged and attaches a
corrected asset built from the main commit. GitHub's autogenerated **Source
code** archives still reflect the original tag, not the repaired extension
asset. The Actions run identifies the precise build source SHA.

For subsequent releases, publish a *new* tag only after its version fields
and release workflow are present in the tagged commit. Do not force-move
published tags just to repair a failed binary upload.
